# 方案 B：笔记任务阶段队列异步化

## 目标

把 `NoteGenerator.generate()` 的同步流水线拆成三段独立队列，每队列独立并发，消除"worker 被 IO 等待阶段（转写/总结）钉住、吞吐量限死为 3 个并发任务"的瓶颈。

## 现状问题

`task_serial_executor`（ThreadPoolExecutor，默认 3 workers）每个 worker 跑**整条**同步链：
```
PARSING → DOWNLOADING → TRANSCRIBING → SUMMARIZING → SAVING → SUCCESS
```
其中 TRANSCRIBING（MLX Whisper 等待）和 SUMMARIZING（LLM HTTP 等待）期间线程被钉住空耗。3 个 worker = 同时只能跑 3 个任务，即使 2 个都在等 GPT 返回，第 4 个任务的下载/转写也排不进去。

## 目标架构（用户已确认：内置 queue + 线程池，转写 worker=1）

```
run_note_task → pipeline.enqueue(task_id, params)
  └─ download_queue (workers=6):   解析链接 + 下载音频/视频
       └─ 产物 {task_id}_audio.json → transcribe_queue (workers=1, MLX单实例)
            └─ 产物 {task_id}_transcript.json → summarize_queue (workers=3)
                 └─ 写 markdown + save_note_to_file + 向量索引 → SUCCESS
```

## 关键设计：用现有缓存文件协议衔接阶段

不引入新协议。各阶段产物天然是 `json_results/` 下的缓存文件：
- 下载阶段 → `{task_id}_audio.json`（AudioDownloadResult）
- 转写阶段 → `{task_id}_transcript.json`（TranscriptResult）
- 总结阶段 → `{task_id}_markdown.md` + `{title}.md`

每阶段从缓存读上阶段产物，写自己的产物给下阶段。与现有缓存逻辑完全兼容，重启恢复逻辑（main.py startup 扫描 stuck → RETRYABLE）无需改动。

## 实现细节

### 1. 新增 `backend/app/services/task_pipeline.py`
`TaskPipeline` 类管理三段队列：
- `enqueue(task_id, ...)` → 提交到 download 池
- 每阶段 worker 执行完把任务交给下一队列（或写 FAILED/RETRYABLE 终态）
- 阶段入口检查 batch_control（PAUSED/CANCELED → 拦截，不进入下一队列）
- 任务终态时清理 `_inflight_video_tasks`
- 并发度通过 env 配置：`PIPELINE_DOWNLOAD_WORKERS`(6)、`PIPELINE_TRANSCRIBE_WORKERS`(1)、`PIPELINE_SUMMARIZE_WORKERS`(3)

### 2. 修改 `backend/app/services/note.py`（NoteGenerator）
把 `generate()` 拆成三个可独立调用且缓存兼容的阶段方法：
- `phase_download(task_id, ...) -> AudioDownloadResult`（含 PARSING + 字幕检查 + `_download_media`）
- `phase_transcribe(task_id, audio_meta, ...) -> TranscriptResult`（含 `_get_transcript`）
- `phase_summarize(task_id, audio_meta, transcript, ...) -> NoteResult`（含 `_summarize_text` + 后处理 + 保存）
- `self.video_path` / `self.video_img_urls` 改为通过返回值传递（不再依赖实例状态跨阶段）
- **保留原 `generate()` 方法**（向后兼容，测试仍可用，内部可映射到三阶段）

### 3. 修改 `backend/app/routers/note.py`（run_note_task）
```
# 原：note = task_serial_executor.run(_execute_note_task)  # 阻塞
# 改：pipeline.enqueue(task_id, ...) ; return              # 异步返回
```
`run_note_task` 不再阻塞。`_inflight_video_tasks` 清理移到 pipeline 终态回调。

### 4. `task_serial_executor.py` 保留但标记 deprecated（测试仍引用 `SerialTaskExecutor`）

### 5. `main.py` startup 恢复逻辑**无需改动**（中断状态 → RETRYABLE 已兼容）

## 批次暂停/取消（改进）

现状：只在任务启动时检查一次，运行中无法中断。
改进：**每阶段 worker 执行前都检查** batch_control。PAUSED/CANCELED 任务在下一阶段入口被拦截，协作式检查（与现有模型一致）。

## 错误处理

每阶段 try/except：`_is_retryable_error` → RETRYABLE，否则 FAILED。与现有 `_handle_exception` 完全一致。

## 验证方案

1. 单条视频笔记生成 → SUCCESS
2. 同时提交 10+ 任务 → 下载并发起数应 > 3
3. 大批量任务 → 转写阶段只跑 1 个
4. 任务在下阶段下载时暂停批次 → 下阶段入口被拦截为 PAUSED
5. FAILED 任务重新提交 → 正常
6. 现有测试（test_batch_note_api / test_duplicate_note_guard / test_task_serial_executor）仍通过
7. 重启中断任务 → RETRYABLE

## 风险与对策

| 风险 | 对策 |
|---|---|
| 三阶段拆分状态不一致 | 用已有缓存文件衔接，不引入新协议 |
| `_inflight_video_tasks` 清理时序 | pipeline 终态回调统一清理 |
| 测试 mock `generate()` | 保留原 `generate()`；新增 pipeline 单测 |
| MLX 内存 | 转写 worker=1 强制单实例 |
